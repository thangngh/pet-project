## Method

- Enumerated all 115 `.ts` files under `backend/src` and read every module
  composition root, controller, guard, middleware and repository.
- Traced each documented runtime mechanism from its entry point to the code
  that consumes it, rather than confirming the code exists.
- Compared `CLAUDE.md`, the roadmap and the gate/checkpoint records against
  what the code does.

That last step is what most of these findings come from. Every one of them is
a component that exists, compiles, has a plausible name, and is not connected
to anything.

## P0 — the application cannot serve its own API

### F01 — Identity is never written to `RequestContext`

`RequestContextService.setIdentity()` has exactly one occurrence in the
repository: its own definition.

```
grep -rn "setIdentity" backend/src
→ shared/adapters/request-context/request-context.service.ts:35
```

`RequestContextMiddleware` writes `requestId` and `correlationId` and nothing
else (`request-context.middleware.ts:10-19`). `JwtStrategy.validate()` returns
the identity onto `req.user`, which is Passport's own property — nothing copies
it into the AsyncLocalStorage store.

So `requestCtx.getIdentity()` returns `undefined` on every request, including a
request with a perfectly valid token.

**Blast radius.** Every endpoint that reads identity from the context rejects
every caller:

| Endpoint | Result today |
|---|---|
| `GET  …/me` | 401 |
| `PATCH …/me/profile` | 401 |
| `POST …/auth/change-password` | 401 |
| `POST …/products` | 401 |

That is the entire User bounded context and product creation. `user.controller.ts:24`,
`:32`, `:40` and `product.controller.ts:41` each read the identity and throw
`UnauthorizedException` when it is missing, which it always is.

**Not affected.** `RolesGuard` and `AttributesGuard` read `request.identity || request.user`
and so see Passport's copy; they are unaffected. Auth's own three endpoints use
`req.user` directly and work.

This is the deepest finding in the audit: the change-password path fixed in
PR #2 and the profile path documented since gate-001 have never been reachable,
for a reason unrelated to either.

### F02 — The global `ValidationPipe` is never registered

`shared/application/pipes/validation.pipe.ts` defines the pipe. Nothing
references it — no `useGlobalPipes` in `main.ts`, no `APP_PIPE` provider in any
module.

```
grep -rn "useGlobalPipes\|APP_PIPE\|ValidationPipe" backend/src
→ only the definition itself
```

DTO classes are erased at runtime unless a pipe instantiates and validates
them, so every `class-validator` rule in the codebase is decoration only.

**Blast radius.** No request body or query is validated anywhere:

- `RegisterDto` — email format, password strength: not enforced
- `ChangePasswordDto` — added in PR #2 specifically to enforce strength: not enforced
- `UpdateProfileDto`, `CreateCatalogDto`, `UpdateCatalogDto`, `CreateProductDto`,
  `UpdateProductDto`: not enforced
- `SearchProductDto` — `@Type(() => Number)` never runs and the field defaults
  never apply, because the DTO is never instantiated → **F10**

It also invalidates a claim I made in `gate-003`: that password strength was
"enforced by the DTOs instead" of the value object. It is enforced by neither → **F06**.

### F03 — No way to create the database schema

`DB_SYNCHRONIZE=false` in both `.env` and `.env.example`, and the repository
contains no migrations directory, no migration files and no TypeORM
`data-source.ts`:

```
find backend -name migrations -o -name '*.migration.ts' -o -name 'data-source*'
→ nothing
```

`package.json` has no migration scripts. So even against a reachable
PostgreSQL, the application starts with no tables and the first query fails.

**Blast radius.** No integration test, e2e test or manual run can work. This is
why "not verified against a live database" has been carried in every checkpoint
since 2026-08-06 — the blocker is not the missing Docker daemon in the agent
environment, it is that there is no schema to create.

### F04 — `docker-compose.yml` databases do not match the application's config

Compose starts three PostgreSQL services:

| Service | Host port | Database |
|---|---|---|
| `postgres_auth` | 5432 | `ddd_auth` |
| `postgres_user` | 5433 | `ddd_user` |
| `postgres_catalog` | 5434 | `ddd_catalog` |

The application opens **one** `DataSource` (`shared/adapters/persistence/typeorm/typeorm.module.ts:8-19`)
using `DB_HOST`/`DB_PORT`/`DB_DATABASE`, which default to `localhost:5432/ddd_project`.
Port 5432 is `postgres_auth`, which has no `ddd_project` database.

`app.config.ts:24-37` declares per-context `database.auth` and `database.user`
blocks. Nothing reads them.

**Blast radius.** `CLAUDE.md`'s documented start sequence — `docker compose up -d`
then `pnpm start:dev` — cannot work. Combined with F03, a new developer cannot
get a running system from the repository as it stands.

Note this is a fork in the road, not just a config typo: either the code grows
three data sources, or compose collapses to one database. That is decision **D4**.

## P1 — security and correctness

### F05 — `@Roles('admin')` is inert

`RolesGuard.canActivate()` returns `true` immediately when `app.features.rbac`
is false (`roles.guard.ts:19-21`), and `FEATURE_RBAC=false` in both `.env` and
`.env.example:42`.

**Blast radius.** Every admin-only write is open to any authenticated user:
create/update/archive catalog (`catalog.controller.ts:25-48`) and
create/update/publish/archive product plus attribute and media mutation
(`product.controller.ts`). Eleven endpoints carry `@Roles('admin')` — eight product, three catalog; none of
them enforces it.

The guard itself is correct and tested. Only the flag is off.

### F20 — Public registration accepts a caller-chosen role

`RegisterDto` declares an optional `role?: 'admin' | 'user'`
(`register.dto.ts:16`). `RegisterUserInput` carries it, and `AuthService.register`
passes it straight into the aggregate: `User.create(email, password, input.role)`
(`auth.service.ts:40`). The endpoint is `@Public()`.

The TypeScript union is compile-time only. The DTO's runtime guard is
`@IsString()` — no `@IsIn(['admin', 'user'])` — and no validation runs at all
today (**F02**), so any string reaches the entity.

```
POST /api/auth/register  { "email": …, "password": "a", "role": "admin" }
```

**Blast radius, and why it matters more than it looks.** Today the damage is
bounded because RBAC is switched off (**F05**) — an `admin` role grants nothing,
since `RolesGuard` returns early. That is the only thing containing it.

The moment `FEATURE_RBAC=true`, self-service privilege escalation goes live
across all eleven admin endpoints. **F05 must not be fixed before F20**, or the
fix makes the system strictly worse than leaving it alone. This is the one
ordering constraint in the audit where getting it wrong is actively harmful.

### F06 — No password policy is in force

Two independent skips compose into one hole:

1. `Password`'s strength check runs only when `hashed` is false
   (`password.value-object.ts:8`), and both call sites construct
   `new Password(hash, true)` — register (`auth.service.ts:38`) and
   change-password. So the VO never validates. → **F15**
2. The DTO rules that were supposed to cover that gap never execute. → **F02**

**Blast radius.** `POST /auth/register` and the change-password endpoint accept
any non-empty string, including `"a"`. Registration is `@Public()`, so this is
reachable unauthenticated.

This is the clearest example of why the findings must be read as chains: each
half was individually defensible, and together they leave no check at all.

### F07 — A disabled feature returns 500, not 503

`GateException extends Error` (`gate-exception.ts:1`) — not `DomainError`, not
`HttpException`. `GlobalExceptionFilter` matches `DomainError`, then
`HttpException`, then falls through to a generic `Error` branch that returns
**500 "Internal server error"** (`global-exception.filter.ts:42-45`).

`CLAUDE.md` states disabled features return 503 with `code: "FEATURE_DISABLED"`.
Neither the status, the code, nor the feature name reaches the client.

**Blast radius.** Every gated endpoint when its flag is off, and every endpoint
when `API_LOCKED=true` — maintenance mode presents as a total server failure,
which is precisely the signal it exists to avoid.

### F08 — Refresh tokens are issued but cannot be used

`AuthService.generateTokens()` returns a `refreshToken` signed with a 7-day
expiry. There is no refresh endpoint (`auth.controller.ts` has register, login,
profile), no rotation, no revocation and no persistence.

`UserSession` — entity, TypeORM entity, repository and `USER_SESSION_REPOSITORY`
token — is fully wired into `UserModule` and injected by nothing:

```
grep -rn "USER_SESSION_REPOSITORY" backend/src
→ only the port definition and the module binding
```

Roadmap Phase 2 lists "Implement RefreshToken" as a task and "Refresh token
rotation works" in its Definition of Done. Neither is done, and both were
recorded as delivered.

**Blast radius.** Sessions end after 15 minutes with no way to extend them; a
leaked refresh token cannot be revoked because none is stored.

### F09 — Archiving a parent catalog leaves its subtree active

`archiveByCatalogId` matches products by their own `catalogId` only
(`product.repository.ts:44`). Nothing walks the tree.

**Blast radius.** Archive a parent catalog: the parent flips to `archived`,
while every child catalog stays `active` and every product under those children
stays `active` and publicly listed. The event flow repaired in PR #3 works
exactly as far as one level.

Catalogs are explicitly a tree — `parentId`, and a tree endpoint that nests to
arbitrary depth — so the single-level behaviour is a defect, not a scope choice.

### F10 — Product search paginates on `NaN`

`SearchProductDto` supplies `page = 1` and `limit = 20` as class field
defaults and converts them with `@Type(() => Number)`. Both require the DTO to
be instantiated by a pipe, which never happens (**F02**).

`GET /products/search` with no query string therefore reaches
`ProductRepository.search()` with `page` and `limit` undefined, and computes
`skip: (undefined - 1) * undefined` → `NaN` (`product.repository.ts:31-32`).

**Blast radius.** The product search endpoint whenever pagination is left to
its defaults — which is the ordinary case, since the defaults exist precisely
so a caller need not supply them.

## P2 — durability and design

### F11 — No outbox, inbox or idempotency store

Roadmap Phase 1 DoD requires an outbox table migration and an idempotency table
migration. Phase 2 DoD requires `ProductPublished` to be written to the outbox.
None of the three tables exists, and `publish-product.use-case.ts` changes
status without emitting anything at all.

**Blast radius.** Both cross-context flows repaired in PR #3 publish in-process
through `@nestjs/cqrs`. If the process dies between the database write and the
handler, nothing retries:

- a catalog is archived while its products stay active
- a user account exists with no profile

Neither is detectable afterwards — there is no record that the event was owed.

This is the largest remaining architectural gap, and the roadmap has asked for
it since Phase 1.

### F12 — Routes are double-prefixed

`main.ts:25` sets a global prefix of `api`. Three of the four controllers then
declare their own: `@Controller('api/v1/products')`, `@Controller('api/v1/catalogs')`,
`@Controller('api/v1')`.

| Controller | Actual path |
|---|---|
| Auth | `/api/auth/...` |
| User | `/api/api/v1/me` |
| Catalog | `/api/api/v1/catalogs` |
| Product | `/api/api/v1/products` |

**Blast radius.** No client can be written against the documented API, and the
two halves disagree with each other. Cheap to fix, but it is a breaking change
to whatever may already call it — decision **D6**.

### F13 — `AUTH_MIDDLEWARE_PORT` is dead, and the documented auth flow is not the real one

`auth-middleware.port.ts` declares `AUTH_MIDDLEWARE_PORT` and
`IAuthMiddlewarePort` with `validateToken` and `validateApiKey`. Nothing
implements it, nothing provides it, nothing injects it. The file survives only
because `AttributesGuard` imports the `RequestIdentity` type from it.

`CLAUDE.md` devotes a section to this port as the mechanism by which every
request is validated and identity reaches `RequestContext`. The real mechanism
is Passport's `JwtStrategy` behind a per-controller `JwtAuthGuard`, and the
identity leg of it was never built (**F01**).

API-key authentication, which the documented port also promises and which the
per-context table assigns to workers and CI, does not exist in any form.

### F14 — Structural drift from the documented architecture

- The Auth BC has no `use-cases/` directory. Register, login, profile and
  change-password all live in `auth.service.ts`, against the documented
  one-file-per-feature rule. Every other context follows the rule.
- `CLAUDE.md` documents `ConflictError`, an `ApplicationError` family
  (`ResourceNotFoundError`, `OperationForbiddenError`, `InvalidInputError`) and
  an `InfrastructureError` family (`DatabaseError`, `ExternalServiceError`,
  `ConfigurationError`). `shared/domain/errors/domain-error.ts` contains
  `DomainError`, `NotFoundError`, `ValidationError` and `UnauthorizedError`.
  The other eight classes do not exist; the filter has no branch for them.
- There is no handling centre (`application/handlers/` dispatchers) in any
  context, and no CQRS split. Both are documented as the intended structure.

### F22 — Three role vocabularies, and the constants file is a trap

Roles are spelled three ways:

| Where | Values |
|---|---|
| `UserRole` in the domain, and the JWT `role` claim | `'admin'`, `'user'` |
| `@Roles('admin')` on eleven endpoints | `'admin'` |
| `application/constants/role.constants.ts` | `'ADMIN'`, `'USER'`, `'SERVICE'` |

Production is self-consistent in lowercase. The constants file is imported by
exactly one place — `roles.guard.spec.ts` — where it is self-consistent in
uppercase, so both pass and neither notices the other.

**Blast radius, deferred but sharp.** Nothing today. But the constants file is
what a reader reaches for when writing the next `@Roles(...)`, and
`@Roles(ROLE_ADMIN)` compares `'ADMIN'` against an identity carrying `'admin'`
— a guard that denies everyone, including admins, with no error and no failing
test, since the only test of that guard uses the same wrong vocabulary.

`ROLE_SERVICE` has no counterpart in `UserRole` at all.

Left as found: spec-002 turns RBAC on and is the change that would walk into
this. It should reconcile the vocabulary to one spelling first — and fix
`roles.guard.spec.ts`, which currently tests a casing production never uses.

### F15 — `Password.isStrongPassword` is unreachable

Covered under F06. Listed separately because the fix is different: F06 is
about restoring enforcement, F15 is about a rule that can never fire in its
current position.

### F16 — No CI, and one placeholder e2e spec

No `.github/workflows/`. Nothing runs build, tests or lint on a pull request —
every figure in every gate artifact comes from a local run by whoever wrote it.

`backend/test/app.e2e-spec.ts` is the Nest scaffold's `GET /` check. There are
no integration tests against a database and no e2e tests of any real flow,
which is what would have caught F01, F02, F05, F07 and F10 in a single run.

### F21 — Two lockfiles

`backend/` contains both `pnpm-lock.yaml` and `package-lock.json`. They were
written by different package managers at different times and cannot be assumed
to resolve the same tree.

`CLAUDE.md` documents pnpm. Whichever CI ends up using (**F16**, none exists
yet), the other lockfile is a trap: a contributor running `npm install` gets a
different dependency graph from one running `pnpm install`, and the `uuid`
omission fixed in PR #1 is exactly the class of bug that hides in that gap.

Delete `package-lock.json`; keep pnpm.

### F19 — Formatting

146 `prettier/prettier` errors. `pnpm lint` is defined as `eslint --fix`, so
running the documented lint command rewrites about 48 files. Any contributor
who lints produces an unreviewable diff.

## Impact chains — what depends on what

The findings are not independent. Fixing them in the wrong order produces work
that cannot be verified.

```
CHAIN A — nothing can be verified end to end
  F03 no schema ──┬──> no integration test, no e2e test, no manual run
  F04 compose ────┘         │
                            └──> blocks proving A, B, C below
CHAIN B — the authenticated API is dead
  F01 identity never set ──> User BC (3 endpoints) + product create: all 401
CHAIN C — nothing is validated
  F02 no pipe ──┬──> F06 no password policy  (with F15 dead VO rule)
                └──> F10 search paginates on NaN
CHAIN D — authorization is nominal, and the obvious fix is a trap
  F05 RBAC flag off ──> 11 admin-only endpoints open to any authenticated user
  F20 self-assigned role ──> anyone can register as admin
       └── F05 currently masks F20. Fix F20 FIRST; enabling RBAC alone
           converts a dormant hole into live privilege escalation.
CHAIN E — delivery is not durable
  F11 no outbox ──> the PR #3 flows are best-effort
  F09 no subtree cascade ──> and correct only one level deep
CHAIN F — the records overstate the system
  F13 F14 F17 F18 ──> gate/checkpoint history cannot be trusted without re-running
```

**Chain A gates everything.** Until there is a schema and a database the
application can reach, no fix to B, C, D or E can be demonstrated — only
argued. That is the position the last three checkpoints have been stuck in.

**B, C and D are independent of each other** and can be fixed in one pass, but
each needs A to prove it. Within D the order is fixed: F20 before F05.

**E is the only chain that is genuinely phase work.** The rest is repair of
things already recorded as delivered.

## What is working

Isolation cuts both ways; these were checked and are sound:

- The container resolves completely, with PR #3 (`app.bootstrap.spec.ts`).
- Both cross-context event flows deliver, proved through the real bus.
- `GateGuard` correctly reads flags and blocks — only its exception mapping is
  wrong (F07).
- `RolesGuard` and `AttributesGuard` implement their logic correctly and are
  tested — only the flag gating them is off (F05).
- `GlobalExceptionFilter` maps `DomainError` subclasses to the right statuses.
- Throttler, helmet, CORS and the Winston logger are registered and configured.
- The domain layer is pure: no package imports under any `domain/`.
- Build 0 errors, 53 tests passing, 0 real lint errors.
